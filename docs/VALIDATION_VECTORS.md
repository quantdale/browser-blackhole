# Physics and rendering validation vectors

This document defines the deterministic scenarios that prove the renderer is solving the intended problem. Exact numeric fixture values should be generated by the converged CPU reference solver and committed with provenance once M2 implementation exists.

## 1. Fixture format

Store machine-readable fixtures under `tests/fixtures/physics/` with a schema similar to:

```json
{
  "schemaVersion": 1,
  "name": "weak-field-b20",
  "convention": "schwarzschild-M1-static-observer",
  "input": {},
  "expected": {},
  "tolerances": {},
  "generator": {
    "commit": "...",
    "method": "rk4",
    "step": 0.0001,
    "convergenceEvidence": []
  }
}
```

Never hand-edit expected numbers without regenerating and recording why.

## 2. Unit/radius invariants

Deterministic scalar tests:

- with `M=1`, horizon = `2`;
- photon sphere = `3`;
- Schwarzschild ISCO = `6`;
- critical impact parameter `3*sqrt(3)`;
- gravitational radius conversion for one solar mass agrees with selected physical constants to documented precision;
- gravitational time conversion likewise.

## 3. Local tetrad vectors

At observer radii such as `r=10`, `r=20`, `r=100` test local rays:

- purely inward radial;
- purely outward radial;
- tangential;
- 30° from inward;
- 60° from inward.

Check null metric norm, derived `E`, `L`, `b`, and sign of radial momentum.

## 4. Radial capture

Observer at a fixed large radius, camera ray exactly toward black-hole center.

Expected:

- `CAPTURED`;
- monotonically decreasing radius to capture threshold;
- near-zero angular momentum;
- finite step count;
- no disk hit when disk disabled;
- no numerical failure.

This is the first end-to-end geodesic sanity case.

## 5. Radial escape

Observer with exact outward radial ray.

Expected:

- `ESCAPED`;
- near-zero angular momentum;
- final direction remains radial;
- no spurious turning point.

## 6. Weak-field deflection series

Use impact parameters much larger than the critical value, e.g. `b=20, 40, 80, 160` with an observer/background arrangement suitable for measuring asymptotic deflection.

Expected leading behavior:

`alpha ~ 4M/b`.

Rather than demanding the approximation equal numerical GR exactly, verify relative error decreases as `b` increases and the sign/orientation is correct.

## 7. Critical capture boundary

Use values around

`b_c = 3 sqrt(3) ≈ 5.196152422706632`.

Fixture sequence should include values safely below/above and progressively closer on both sides.

Expected:

- below critical boundary (for the selected asymptotic setup) -> capture;
- above -> escape after strong bending;
- increasing winding/step demand as `b -> b_c`;
- no silent non-finite values.

Exact near-critical cases may be excluded from low-quality GPU acceptance if f32 cannot meet reference tolerance; they remain debug/stress fixtures.

## 8. Spherical-symmetry rotations

Take one Schwarzschild observer/ray configuration and rotate the entire camera/background setup around arbitrary axes while preserving relative geometry.

Expected scalar observables:

- classification unchanged;
- minimum radius unchanged;
- winding unchanged;
- deflection magnitude unchanged.

This catches world-axis leakage in the geodesic solver.

## 9. Camera reconstruction vectors

At fixed viewport/FOV verify rays for:

- center;
- four corners;
- midpoint of each edge;
- odd and even resolutions;
- portrait and landscape aspect ratios.

CPU camera reconstruction and shader selected-pixel probe should agree within f32 tolerance.

## 10. Disk crossing geometry

With an equatorial thin disk and several camera inclinations:

- direct near-side hit;
- far-side lensed hit;
- ray that crosses disk plane inside the inner hole -> no hit;
- ray that crosses outside outer edge -> no hit;
- grazing crossing near inner radius;
- trajectory producing a higher-order disk image.

For each committed fixture store hit world position, radius, and path/winding indicators.

## 11. Disk convergence

For a selected grazing/high-curvature disk ray, generate results at successively tighter integration/refinement settings.

Expected disk hit radius/position converges. Production tolerance must be selected from this evidence rather than appearance.

## 12. Static gravitational redshift

Before orbital Doppler, use a static emitter and static observer where an analytic Schwarzschild gravitational frequency ratio is available:

`nu_obs/nu_emit = sqrt(f_emit / f_obs)`

for the appropriate static positions/sign convention.

Use this to validate `-k·u` implementation independent of disk rotation.

## 13. Circular-orbit emitter

At several radii `r >= 6`, verify:

- `Omega = sqrt(M/r^3)`;
- four-velocity normalization `u_mu u^mu = -1`;
- `u^t = 1/sqrt(1-3M/r)` for Schwarzschild circular geodesic;
- direction reversal swaps approaching/receding Doppler ordering.

## 14. Face-on disk symmetry

Observer aligned with disk normal.

Expected:

- azimuthal first-order approaching/receding Doppler asymmetry is absent/symmetric in the idealized model;
- radial temperature/emissivity remains symmetric;
- any procedural turbulence must be disabled/frozen for this test.

Use image-level radial/rotational comparison with tolerance, not only a human screenshot.

## 15. Inclined disk Doppler ordering

At high inclination, identify known approaching and receding regions from the disk velocity convention.

Expected:

- approaching side has larger `g` than corresponding receding side;
- scientific radiance follows the documented transformation;
- toggling Doppler for education mode removes the kinematic asymmetry while leaving gravitational lensing intact.

## 16. Scale invariance

Normalized mode:

- preset A mass `10 M_sun`;
- preset B mass `10^8 M_sun`;
- all positions/radii specified identically in `r_g`.

Expected camera rays in normalized coordinates, geodesic classification, disk hit geometry, and normalized scientific image are equal within deterministic render tolerance. Physical-unit labels/times differ.

Physical mode:

- hold observer physical distance fixed while changing mass.

Expected normalized observer distance and angular/lensing appearance change consistently.

## 17. Background mapping

With gravity disabled/debug straight-ray mode, environment sampling should match canonical cubemap/procedural directions. Enable gravity and confirm escaped direction, not original camera direction, drives the sample.

## 18. Failure fixtures

Create intentionally pathological test inputs:

- observer too near/inside unsupported horizon state;
- NaN state injected through test API;
- max steps intentionally tiny;
- disk crossing with zero normal;
- invalid LUT manifest;
- backend/device initialization failure.

Expected behavior is explicit error/failure visualization, never a silent black canvas.

## 19. GPU selected-pixel comparison

For a curated set of pixels from deterministic presets, compare GPU diagnostics to CPU reference:

- classification: exact;
- minimum radius: absolute/relative tolerance;
- disk radius: tolerance;
- escaped direction: angular tolerance;
- `g`: relative tolerance;
- winding: tolerance excluding intentionally chaotic near-critical fixtures.

Store tolerance by quality tier if needed.

## 20. Visual golden suite

Minimum eventual goldens:

- diagnostic camera ray pattern;
- star field without gravity;
- Schwarzschild lensing/no disk;
- face-on thin disk;
- high-inclination thin disk;
- Doppler scientific view;
- classification debug;
- step-count debug;
- cinematic hero preset;
- LUT equivalent of a numerical preset;
- Kerr spin-zero comparison;
- high-spin prograde view.

Goldens are captured with fixed browser build/container where possible. Visual diffs are not substitutes for physics fixtures.

## 21. Performance benchmark presets

Maintain deterministic scenes with increasing complexity:

- `BENCH_EASY`: no disk, far observer, weak critical region;
- `BENCH_TYPICAL`: inclined disk and representative view;
- `BENCH_CRITICAL`: large photon-ring/strong-field screen coverage;
- `BENCH_POST`: heavy post-processing but simple geometry;
- `BENCH_KERR` later.

Every performance claim names preset, viewport, effective resolution, backend, GPU, browser, quality settings, and sample count.

## 22. Acceptance tolerance policy

Do not invent one universal epsilon. Use quantity-aware tolerance:

- scalar constants: near machine precision on CPU;
- normalized vectors: angular/norm tolerance;
- GPU f32 geodesic observables: empirically established against converged CPU fixtures;
- classifications: exact outside explicitly marked near-critical ambiguity bands;
- visual images: perceptual/pixel threshold plus physics probes;
- performance: statistical ranges rather than exact frame times.

Tolerances may only be loosened with documented evidence explaining why the old threshold was invalid.
